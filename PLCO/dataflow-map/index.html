一、五個環節怎麼串起來

① 資料來源 — 誰在產生資料

資料分成兩類性質完全不同的來源，這個區分在會議中很重要：主觀資料（選手每日自陳的疲勞、壓力、睡眠、痠痛、RPE）與客觀資料（穿戴裝置、GPS、體能檢測、醫療診斷、比賽統計）。PLCO 的產品敘事核心，正是把這兩類合併後一起判讀。

值得注意的是，主觀資料的量最大、頻率最高，也最便宜，但同時最脆弱——依從性一掉，整個系統的輸出就失真。這是所有 AMS 導入最常見的失敗點。

② 輸入通道 — 資料怎麼進到系統

四條路徑：選手用 PLCO Player 自己填、教練用 PLCO Coach 輸入課表與觀察、醫療與體能人員在團隊後台記錄、以及透過 connector／API 從外部裝置和系統自動匯入。

前三條是人工輸入，靠的是流程與文化；第四條是技術整合，靠的是 connector 覆蓋率。第四條打上紅旗，因為公開資料只說「可整合」，沒有完整支援清單與 API 文件。

③ 平台核心 — 資料在裡面被做了什麼

這一層是 PLCO 的價值主張，也是最不透明的一層。可拆成五塊：

  • 資料整合與標準化：不同來源的選手 ID、單位、時間軸要對齊，缺失值要處理。這塊做不好，後面全部無效。
  • 指標計算：訓練負荷、負荷變化率、可用率等——這是規則明確、可驗算的部分。
  • 模型與風險判讀：準備度、疲勞、傷病風險分數。這是統計／機器學習判斷，紅旗——目前沒有公開的驗證方法與表現指標。
  • 治理層：角色權限、同意、未成年處理、保存期限、稽核、資料託管地點。紅旗——政府與健康資料合作的前提。
  • PLCO PASS：選手身分與資料的跨隊、跨層級延續（青訓 → 職業）。這在體系化的國家層級應用上其實很有價值。

④ 產出物 — 系統吐出什麼

六種產出對應六種使用情境。特別要區分兩件事：給人看的（儀表板、警示、報表、個人回饋）與給系統用的（匯出與 API）。前者決定日常好不好用，後者決定 TISS 能不能真正擁有自己的資料。匯出與 API 打上紅旗，因為公開資料看不出匯出格式、粒度與資料模型。

⑤ 決策與行動 — 誰因此改變了行為

這是整張圖真正的終點。系統本身不創造價值，只有當教練真的改了課表、防護員真的改了介入、選手真的改了睡眠行為時，價值才發生。PLCO 對外的定位也是「教練決策助手」而非取代教練，這與 TISS 的人機協作情境相容。

回饋迴路 — 為什麼這是一個循環而非直線

今天的決策改變了明天的訓練與身體狀態，明天的訓練又產生新一輪資料。這個迴路的轉一圈的時間決定了系統有沒有用：如果選手早上填報、教練當天下午才能看到判讀，那就來得及調整；如果要等一週，這套系統就只剩事後檢討的價值。這是會議中值得問的一個實務問題。

圖右下角那個虛線框是整件事的關鍵。TISS 的目標是建立自己的運動資料分析與追蹤平台。因此「PLCO 產出的資料能否以原始粒度、附資料字典、無額外費用地完整回流到 TISS 自有平台」，比任何單一功能是否好用都更重要。若這條虛線接不通，PLCO 就只能是流程學習與 PoC 的對象，不能是平台底座。

三、用這張圖問問題的三個切法

  1. 順著走：請對方拿一位真實選手（去識別化），從他早上打開 App 開始，一路走到教練當天下午做了什麼決定。走得順不順，比任何簡報都誠實。
  2. 逆著走：指著「風險提示與建議」問——這個提示背後用了哪些欄位？哪些是主觀、哪些是客觀？缺一項會怎樣？這能快速測出模型的透明度。
  3. 橫著切：問同一份資料在教練、防護員、選手、管理層四種角色下，各自看到什麼、看不到什麼。這同時測出權限治理與產品成熟度。
