這個 skill 做什麼

需求方在一評會議上要委員審的是需求本身：範圍夠不夠、期程撐不撐得住、規格會不會做不出來。 所以這個 skill 的產出不只是投影片，而是三件事：

① 把規範書搬上投影片

11 種預先設計好的版型，涵蓋封面、功能總覽、流程、期程、配分等一評必備頁面。

② 對帳找出文件落差

交叉比對規範書內文、系統功能架構圖、各附件，找出彼此對不起來的地方。這是唯一超越「搬字」的一步。

③ 收斂成委員裁示題

落差清單變成必出的「提請委員指導事項」頁，每題寫成委員可當場回答是或否的問句。

frontmatter 設了 disable-model-invocation: true —— 模型不會自己判斷要不要用它，必須由你明確輸入 /procurement-deck 才會啟動。

快速開始

1. 建立環境（只需一次）

bash ~/.agents/skills/procurement-deck/scripts/setup.sh

會在 skill 目錄下建 .venv 並安裝 python-pptx 與 Pillow， 然後把 venv 的 python 路徑印到 stdout。已存在就直接回傳路徑、不重裝。 後續所有指令都用這個 python 執行。

2. 跑一次完整範例

PY=$(bash ~/.agents/skills/procurement-deck/scripts/setup.sh)
$PY ~/.agents/skills/procurement-deck/examples/venue_booking.py out.pptx
$PY ~/.agents/skills/procurement-deck/scripts/render.py out.pptx ./preview

venue_booking.py 是實際交付過的 17 頁簡報，涵蓋全部版型； render.py 會輸出每頁 PNG 與溢版清單。

3. 寫自己的 build script

import sys, os
sys.path.insert(0, os.path.expanduser("~/.agents/skills/procurement-deck/scripts"))
from deck import Deck, text, shape, badge, card, note_strip, \
                 PRIMARY, ACCENT, AMBER, GREEN, WHITE, MARGIN, BODY_TOP

d = Deck()

d.cover(
    eyebrow="○○機關　／　115 年度採購案（案號 115-XX-XXX）",
    title_lines=[("運動場地", WHITE), ("預約平台", ACCENT)],
    subtitle="建置案　需求規範書說明",
    meta=["一評審議會議　／　需求單位簡報"],
    facts=[("預算經費", "XXX 萬元（含稅）"),
           ("履約期限", "決標日翌日起至 1XX/XX/XX")])

d.detail_list("03　／　Scope", "用戶端功能需求", [
    ("場地搜尋", "依縣市、運動類型、日期與時段查詢可預約場地"),
    ("線上預約", "引導式流程完成時段選擇、設備租借與確認")])

d.save("out.pptx")

每個版型函式都回傳 slide 物件，可以再用 text() / shape() 疊加內容。

六步流程

SKILL.md 定義的工作程序。每一步都有完成條件，沒過不能進下一步。

  1. 收齊來源

    讀規範書全文，並在同一資料夾找齊四類文件：

    • 簽呈 — 案號、招標方式、預算核定狀態、是否召開一評
    • 勞務明細表／規格表 — 採購性質、驗收方式、付款比例、擴充條款
    • 廠商估價單 — 經費組成（第 15 頁的來源）
    • 既有同類簡報 — 該機關辦過類似案的話，版型與用語照它走
    完成條件：四類各自標記為「已讀」或「不存在」。

  2. 對帳

    把規範書內文、系統功能架構圖、各附件三者交叉比對，找出彼此對不起來的地方。這是整份簡報唯一超越「把文件搬進投影片」的一步，也是委員最想聽的內容。

    完成條件：落差清單每項註明出處（頁碼或節次）。不足 3 項就逐節再走一次；仍不足則據實記錄——捏造落差比漏掉落差更糟。

  3. 排頁

    依 17 頁骨架決定頁次，逐頁指定版型函式與內容來源。骨架沒有的頁，先用 dump_layout.py 拆 assets/ 裡的既有簡報，找形狀相近的版面照座標重建。

    完成條件：一份頁次表，每列有「頁次／版型函式／內容取材」。

  4. 建置

    寫 build script，sys.path 加入 scripts/ 後 from deck import ...。第 2 步的落差清單在此收斂成 qgrid 頁——這頁必出。金額、日期、數量、等級照抄規範書原文。

    完成條件：script 執行成功並輸出 pptx。

  5. 驗版

    python scripts/render.py <deck.pptx> <outdir>

    逐頁看過 PNG，找四類問題：文字溢出容器或壓到邊界／卡片下半大量留白／左右欄高度失衡／元素重疊。修正後重跑。中文斷行寬度靠估算不準，這步每一輪都會抓到東西。

    完成條件：溢版清單為空，且每一頁 PNG 都經檢視。未通過此步不回報完成。

  6. 交付

    pptx 存進專案資料夾，檔名含案名與用途。回報時逐項說明「提請委員指導事項」各題的依據，並標示哪些內容取自規範書原文、哪些是對帳推論。

    完成條件：回報中每題議題都標明依據來源。
為什麼要區分原文與推論？ 委員會把簡報上的文字當成需求方的正式立場，推論被誤認成定案會出事。

對帳：六類常見落差

「提請委員指導事項」頁的題目從這裡長出來。依過往兩案，落差集中在：

#落差類型典型徵狀
1內文與架構圖不一致架構圖有的模組，服務內容條列漏列（或反之）
2範圍邊界未言明金流、電子發票、電子票證、簡訊費用由誰負擔、資料移轉
3規模參數無依據會員數、並發數、資料量寫了數字但沒說怎麼估的
4期程與工作量不相稱決標日推遲後，實際可用工作天是否還撐得住交付表
5外部相依的權責要串接的既有系統，其規格文件、測試環境、支援窗口誰提供、何時到位
6驗收標準不可測「功能正常運作」這類無法判定通過與否的條件

17 頁標準骨架

預算 300–600 萬、單一系統建置案的預設頁次。取材欄找不到來源就是規範書的缺口，寫進對帳清單；上限超過就拆頁或砍內容，不要壓字級。

#版型目的取材上限
1cover案名、預算、期限、招標方式一眼看完規範書「專案概述」＋簽呈事實面板 4 格
2agenda讓委員知道待會會被問到什麼本簡報自身結構6 張卡
3contrast為什麼要做：痛點 → 解方規範書「專案目的」，痛點多半需自行歸納左右各 4 條、每條 ≤ 32 字
4section＋自繪本案在既有系統版圖的位置、對外介接對象規範書「架構說明」的系統功能架構圖中央本案 + 左右各 1 既有系統
5columns功能總量一頁看完，建立範圍共識規範書「服務內容」逐條3 欄 × ≤ 10 條、每條 ≤ 14 字
6–8detail_list每項功能一句話講清楚做什麼同上，逐條展開每頁 8–10 項、說明 ≤ 30 字
9flow使用者主流程與例外分支規範書功能列表推導；例外分支常需自行補5–7 步 + ≤ 3 分支
10section＋雙卡系統規格、效能規模、資安責任規範書「系統規格」「資通安全責任」左卡 6 條、右卡 4 組數據
11timeline分幾期交付、每期交什麼、付多少規範書「履約期程及交付項目」表 1＋「付款條件」2–3 期、每期 3 項交付
12section＋雙卡保固範圍與教育訓練義務規範書「保固服務」「教育訓練」＋保證金左右各 4 項
13section＋雙卡廠商門檻與人力底線規範書「廠商履約規範」「服務建議書內容與規格」左右各 4 條 + 底部人力列
14scorebar配分權重是否合理規範書「評選須知與評分標準」表 25–6 列，依配分由高到低
15section＋自繪預算怎麼編出來的廠商估價單＋勞務明細表3 項組成
16qgrid必要頁：請委員裁示的待確認議題對帳清單6 題、每題 ≤ 60 字
17closing收尾與聯絡窗口規範書「聯絡方式」2 行標語

依案子調整

  • 預算 < 200 萬或功能 < 15 項：6–8 頁合併成單一 detail_list，砍第 4、15 頁 → 約 11 頁
  • 多期程或含擴充條款：第 11 頁後補一頁 columns 呈現年度路線（範例 1 第 13 頁有現成版型）
  • 純研究或標準制定案（非系統建置）：5–8 頁改為 columns 工作項目總覽 + 每個工作包一頁（範例 1 的 WP 頁型）

工具腳本

render.py — 驗版

python scripts/render.py <deck.pptx> <outdir>

用 Pillow 近似重繪成 slide01.png…，並在 stdout 列出溢版清單 （格式：S 7 溢版 88pt / 容器 62pt @(0.42,3.10) 文字開頭…）。 字型換成系統黑體，字寬與 PowerPoint 有幾個百分點誤差， 抓的是版面問題不是最終外觀：文字溢出容器、卡片大量留白、左右欄失衡、元素重疊。

這台機器上 PowerPoint 的 AppleScript 匯出被 sandbox 擋住、也沒裝 LibreOffice， render.py 是唯一可用的驗版途徑。最終外觀仍以 PowerPoint 開啟為準。

dump_layout.py — 拆解既有簡報

python scripts/dump_layout.py <deck.pptx> [起始頁] [結束頁]

印出每個形狀的座標、尺寸、字級、色碼、文字。用途是把 assets/ 裡的舊簡報當版型來源——找到適合的頁，照它的座標與層次重建，而不是憑空發明新版面。

setup.sh — 環境

bash scripts/setup.sh   # 印出 venv python 路徑；已存在則直接回傳

設計系統

deck.py 已把這些寫死成常數，只有自繪版面或新增版型時才需要查。

版面基準線

  • 10 × 5.625 in（16:9）
  • 左右安全邊界 MARGIN = 0.38
  • 頁首佔 0–1.06，內容區 BODY_TOP = 1.22 到 BODY_BOTTOM = 5.38
  • 卡片間距 0.15–0.16；卡片內縮 0.18–0.22

色票

PRIMARY · 1C5FA5卡片標頭、第一類別、強調文字
ACCENT · 3B82C4頁首短線、第二類別、封面第二行標題
DARK · 1A1F2E深底頁、主標題文字
BODY · 4A5268內文
MUTED · 8A90A2標籤、註腳、深底頁小字
AMBER · D97706金額、付款、待確認議題頂線
GREEN · 2E8B57第三類別、資安
LIGHT · E8F1FAbadge 底色
PALE · F5F8FC面板、註記條底色
BORDER · D8E3F0卡片外框、分隔線
LINE2 · C5D9F0流程線、箭頭、序號浮水印
分類用色固定按 PRIMARY → ACCENT → GREEN 的順序，跨頁保持同一類別同一色。 例：用戶端永遠 PRIMARY、供應商端永遠 ACCENT、平台端永遠 GREEN。

字型與字級

中文 Microsoft JhengHei、西文與數字 Calibri，由 _style_run() 同時寫入 a:latin 與 a:ea，Mac 與 Windows 的 Office 都內建。

級數用途

估行數的比例：中文字寬約等於字級 —— 11 pt 的字在 4.0 in 寬的框裡一行約 25 字。 用這個算，不要靠感覺。

寫作顆粒度

規範書條文是法律語言，投影片是口語。轉換時：

  • 條列項目名保留規範書原詞（委員會照條文對），說明句改寫成白話
  • 一句說明講「做什麼」，不講「怎麼做」——技術方案是廠商的事，不是需求方的事
  • 金額、日期、數量、等級一律照抄原文，不換算、不四捨五入
  • 規範書寫「基礎版」「基礎功能」「基礎流程」的地方保留「基礎」二字，那是範圍界線

注意事項

qgrid 頁不可省

「提請委員指導事項」是必出頁。每題要寫成委員可以當場回答是或否的問句，不是開放式感想。

不要壓字級來塞內容

超過骨架表的上限就拆頁或砍內容。字級是設計系統的一部分，改了整份簡報會失衡。

驗版沒過不算完成

溢版清單必須為空，且每一頁 PNG 都要實際看過。中文斷行估不準，這步每輪都會抓到東西。

寧可少一項也不要編造

對帳落差不足 3 項時據實記錄。捏造落差比漏掉落差更糟——委員會拿它當需求方的正式立場。

回報要標示依據

哪些取自規範書原文、哪些是對帳推論，逐項講清楚。推論被誤認成定案會出事。
